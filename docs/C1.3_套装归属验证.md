# C1.3 套装归属与包级分类验证

**性质**：只读研究。未改生产代码、正式分类、用户分类、缓存与分类树。
**样本**：U 盘 110 个 vpk 中抽取 40 个人工核验；全部基于实际文件内容与元数据。
**方法**：读目录表 + addoninfo + 资源名重合 + 跨包引用；不解析 VMT/MDL 内容（沿用 C1.1 边界）。

---

## 0. 结论

1. **归属证据在本语料里极其稀薄**：110 个包里只有 1 个带 addoninfo 标题、0 个带作者；跨包**直接引用**只找到 1 组（⑨ 套装里的 2 号 PCF 引用 1 号的 6 个材质）。
2. **文件夹几乎不能当证据**：27 个多包目录里，17 个是「杂项功能」这类分类目录，装的是互不相关的 MOD；按文件夹归组会把 17 个独立 MOD 并成一套。
3. **共享资源名要过滤官方名才能用**：`v_rifle_ak47.mdl`、`spitter.vmt` 这类官方名会让任意两个 AK/特感包「重合」；过滤后真正的同源证据只有几组（洛可可/MWIII Mac-10、蕾缪安/DeepSeek、桃夭/印花 sg552），且它们指向「同基座」，不是「同一套」。
4. **能证明的套装只有 2 套**：霓虹天使医疗包（7 件共享 6 个自定义材质名）、⑨（1+2 号直接引用）。Scattershot 4 件**共享资源为 0**，只是同系列命名。
5. **第三个改判案例的结论**：粒子类型判定正确；与 2 号同组有直接证据；与 3 号（模型件）仅弱证据 → **保留 Shadow 的特效结果，标记归属不确定**，不改分类。

## 2. 归属证据分级（经真实样本检验）

| 级 | 证据 | 定义 | 本语料实例 | 单独可否定归属 |
|---|---|---|---|---|
| A | 跨包直接引用 | 一个包的资源内容里写着另一个包的文件名 | ⑨#2 的 PCF 引用 ⑨#1 的 `beam_lightning_o3` 等 6 个材质 | 可以 |
| B | 共享非官方资源名 + 资源互补 | 两包含有相同自定义文件名，且一个带模型、一个带材质/贴图 | 霓虹 7 件共享 `halo_*.vmt`；印花/桃夭共享 50 个自定义名 | 可定「同源」，不能定「同一套」 |
| B- | 同元数据 | 同 addoninfo 标题或作者 | 语料几乎不可用（1 个标题、0 作者） | 可以，但本语料没有 |
| C | 命名/目录相似 | 同文件夹、同名前缀、编号 1/2/3 | Scattershot 1-4、火光消除 1-3、⑨ 三件 | **不可以** |

实测反例：

- `杂项功能` 目录 17 个包彼此无关，按目录归组会错 16 次。
- Scattershot 1-4 名字最像，**共享资源 0**，是四件独立发布。
- 洛可可与 MWIII 共享 59 个自定义材质（B 级），但它们是两套不同皮肤 → B 级只证明「同基座」。
- AWP 可畏与初音 AWP 只共享 `v_snip_awp.mdl` 这类官方名 → 过滤后重合 0。

## 3. 第三个改判案例：⑨琪露诺 1 号

| 问题 | 答案 | 依据 |
|---|---|---|
| 1 粒子类型判断是否正确 | 是 | 239 条 VMT 全在 `materials/particle/*`，86% 贴图指向 `particle/`，无模型 |
| 2 是否独立发布 | 否，至少与 2 号同组 | 2 号 PCF 字符串里有 6 个 1 号材质名 |
| 3 是否存在关联模型包 | 有候选（3 号），未证实 | 3 号含 `v_shotgun_chrome.mdl`、`tiepen.mdl` |
| 4 关联依据 | 1↔2 直接引用；1↔3 只有同目录同名前缀 | A 级 vs C 级 |
| 5 证据能否本地可靠获取 | A 级可以；C 级只能得「疑似」 | 引用来自文件内容；目录名是人为整理 |
| 6 是否只靠套装名/目录 | 1↔3 是 | 无共享资源名、无 addoninfo、无交叉引用 |
| 7 归属不确定时怎么办 | 保留特效结果 + 标记归属不确定 | 类型证据成立，包级主体不成立 |
| 8 若未来确认同套装 | 只在套装层补「主体=铁喷 + 影响面」，不改单包 Subject | 单包内容确实只有粒子 |

结论：1 号是「特效组件」（与 2 号同组），与 3 号的套装关系**未证实**。Shadow 判「杂项/特效」正确；缺的是归属字段，不是分类字段。

## 4. 三层关系设计

```
资源类型 AssetKind      mdl / vmt / vtf / pcf / wav / bsp / script / unknown   ← 事实
归属 Attribution        Standalone / Component / MultiSubject / Unknown        ← 推断 + 证据
   ├ SetRef（可空）      套装标识（folder + name prefix 生成，不等于目录本身）
   └ Evidence[]         每条带 A/B/C 级与来源
主体 Subject            对象或对象集合（可空）                                 ← 推断
分类 Classification     大类/小类（展示用）                                     ← 决策
```

规则：

- `AssetKind` 不直接决定 `Subject`，只决定「名字证据能不能进 Subject」（C1.1 的类型否决）。
- `Attribution` 不改变 `Subject`，只解释「这个 Subject 是套装的一部分还是全部」。
- `Classification` 消费 Subject 与 AssetKind；归属只作为备注与影响面，不参与打分。

## 6. 最小实现建议

只做四件事，不建库、不建图：

1. `AttributionStatus` 枚举 + `SetRef`（可空），挂在 Shadow 结果上，不写 ModItem。
2. 证据只收三种：跨包引用（A）、自定义名重合 + 互补（B）、目录/前缀（C）。
3. 判定：有 A → Component（确定）；只有 B → Component（同源，待确认）；只有 C → Unknown（附「疑似套装」）。
4. 输出：分类不变，只多一列归因；套装层汇总留给展示端。

明确不做：MOD 名称库、关系图数据库、跨包指纹合并、按目录自动并组。

## 7. 是否进入 C1.4

**建议进入，但缩小范围**：C1.4 只做「结构化结果 + 归属字段（Shadow）」，不做套装合并、不改正式分类。

理由：结构化的收益已被 C1.1/C1.2 证明；套装合并的证据在本语料里不足以支撑自动决策（2 套可证，多组只有 C 级）。

前置条件：先人工确认 ⑨#1/#3 是否同套（需要作者发布页或安装说明，本地文件无法证明）；否则 ⑨ 只能停在「组件 + 归属不确定」。
