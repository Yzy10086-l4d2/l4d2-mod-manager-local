## 0. 摘要

先给结论，再给依据。

1. **VMT 对「认对象」几乎没有增量。** 12 个包共 81 条 VMT：32 条路径自带可识别词，48 条只能靠模型贴图名挂上去，1 条谁都挂不上；**patch 型材质 0 条**。更关键的是，32 条「自带词」里有 **2 条是假阳性**，都来自同一个子串 `ammo`：`m_mtl_ammo_sat_762n.vmt` 被判成「弹药」、`att_ammo_blk_acharlie300_v8.vmt` 也被判成「弹药」——前者在一个 15 发木狙包里，后者在一个 SCAR-L 包里，都是枪上的弹匣/弹药箱贴图。
2. **MDL 头部的真正价值是「内部名抗改名」，不是贴图名。** 实测：`models/v_models/v_desert_rifle-1.mdl` 的内部名仍然是 `v_models\v_desert_rifle.mdl`——文件被改名了，模型自己还记得它是谁。这是目前唯一一个「不依赖路径写法」的对象证据。
3. **MDL 贴图名不能直接当对象证据。** 68 个贴图名里 6 个命中现有词表，其中 4 个是 `ammo` 类假阳性，有效 2 个（`smg_A`、`V_Shotgun_A`）。而且贴图名会继承：`铁盆改视角` 用的是木喷的贴图组（`V_Shotgun_A` / `V_Shotgun_wood`），只按贴图名判会把「铁喷」判成木喷系。
4. **真正可用的新能力是「关联链」**：MDL 贴图表 → 同名 VMT → `$basetexture` → VTF。本机 81 条 VMT 里 48 条是靠这条链才挂到模型上的（例如睦月包的 `materials/mw23/.../xmaterial_*.vmt` 路径里没有任何游戏对象词，只能通过模型贴图名对上）。
5. **不夸大收益**：这 12 个包里，现有路径法**全部判对**（与 `docs/识别基线.tsv` 记录一致）。B 阶段能交付的是「更稳、更可解释、边界更清楚」，不是「识别率翻倍」。凡是说「通用识别能力已解决」的，都是没跑过样本。
7. **用 U 盘上 110 个包复验（§8.3、§9.4）**：方向没变，但数字更能说明问题。VMT 的 `$basetexture` 在 1761 条可解析条目里只贡献 **1** 条独立识别；MDL 内部名与条目名不一致 **14/168**，其中 2 个条目名完全无信息（`tiepen.mdl` → `v_shotgun_chrome`、`wmcapple.mdl` → `w_eq_medkit`）；另有 **22/110（20%）** 的包在任何资源层都没有可识别信号（纯音效、纯粒子、喷漆、HUD 屏幕）。

6. **优先级由此确定**：MDL 头解析（便宜、抗改名）> 关联图（把孤立文件变成有上下文的资源）> 证据引擎（把早退换成裁决）> VMT 参数标签（识别换色/发光意图）> VMT 内容关联（收益最低，最后做）。

## 2. B1 通用知识模型

### 2.1 分五层，各层只回答一个问题

| 层 | 回答什么 | 形态 | 现有对应物 |
|---|---|---|---|
| Ontology | 游戏里有哪些对象 | 对象表（ID、类型、槽位、官方资源模式） | `Positions` 的 83 行（只有名字，缺属性） |
| Lexicon | 这个对象还叫什么 | 别名表（中文口语、英文、旧名、缩写） | `Positions.Aliases` + `AliasKeys` |
| AssetSchema | 这种文件能说明什么 | 格式 → 可提取字段 → 证据级别 | 无 |
| Relations | 资源和对象怎么连 | 有向边（模型→材质→贴图、对象→官方路径） | 4 条目录约定 |
| Policy | 证据怎么裁决 | 通用算法，不含具体对象 | `Dict` 的表序（隐式） |

### 2.2 对象不是「一行名字」，是「带官方资源模式的一条记录」

```csharp
sealed class GameObject {
    string Id;                 // "shotgun_chrome"
    string Display;            // "铁喷"
    string Category;           // "枪械"
    string SlotGroup;          // "霰弹枪"
    string[] Aliases;          // {"铬制","铁盆"}
    AssetPattern[] Official;   // 官方资源长什么样
    Relation[] Relations;      // 同组变体 / 所属角色 / 配套 HUD
}
sealed class AssetPattern {
    string Glob;               // "models/v_models/weapons/v_shotgun_chrome.mdl"
    MatchKind Kind;            // Exact | Segment | Prefix | Contains
    EvidenceTier Tier;         // T0 结构 / T1 槽位 / T3 名称
}
```

要点：**把「路径长什么样」从规则表搬进对象**。现在的 `Dict` 里 `{"shotgun_chrome","铁喷"}` 是一条匹配规则；改完之后它是「铁喷」这个对象的一条官方资源模式，匹配算法对所有对象一视同仁。

### 2.3 知识如何参与未知 MOD 识别（不是静态表）

三条机制，缺一不可：

1. **Slot Prior（槽位先验）**：一个包如果带了 `v_shotgun_chrome.mdl`，它替换的就是「铁喷」这个槽位——这是 L4D2 的加载机制，不是命名习惯。对象表里记下每个槽位的官方模型名，就能把「文件名」升级成「槽位证据」（T1）。
2. **Relation Traversal（关系遍历）**：路径失效时，从资源出发沿边走。模型 → 贴图表 → 同名 VMT → `$basetexture`。睦月包就是靠这条：VMT 路径 `materials/mw23/weapons/acharlie68/xmaterial_*.vmt` 里没有任何对象词，但它挂在 `v_desert_rifle.mdl` 上（T2）。
3. **Conflict Arbitration（冲突裁决）**：证据分级后由通用算法裁决，不由「谁先扫到」决定。详见 §6。

## 3. B2 统一资源描述

### 3.1 四层分离（互不越界）

```
RawAsset      事实：路径、扩展名、大小、所在包、归档号     ← 只读，不做判断
ParsedAsset   解析：VMT 的 shader/$basetexture、MDL 的内部名/贴图表
Hypothesis    推断：这个资源可能属于哪个对象，附证据
Classification 决策：大类 / 小类 / 槽位 / 状态
```

现有代码的问题是第 2 层根本不存在，第 3 层（Subject）直接由第 1 层算出，第 4 层（Cat/Sub）又另算一遍，两套判定在 `RefineBySubject` 里互相打补丁。

### 3.2 解析器契约（安全边界写进接口）

```csharp
interface IAssetParser {
    string[] Extensions { get; }
    int MaxBytes { get; }          // 单文件读取上限，超出即跳过
    ParsedAsset Parse(byte[] raw); // 纯函数：不写盘、不执行、不联网
}
```

- 输入是**已经读进内存的字节**，解析器没有文件句柄，物理上无法改包。
- 超限直接返回 `null`，并记一条 `Skipped(reason)`，不抛异常给上层。
- 所有字段解析用长度校验 + try/catch，坏文件退化为「无信息」，不拖垮整包。

## 5. B3 资源关联

### 5.1 图模型

节点 = 资源或对象；边 = 五种，带类型与权重：

| 边 | 方向 | 来源 | 强度 | 处理什么 |
|---|---|---|---|---|
| `Contains` | 包 → 资源 | 目录表 | 事实 | 资源归属 |
| `References` | VMT → VTF | `$basetexture` | 强 | 材质→贴图 |
| `NamedBy` | MDL 贴图名 ↔ VMT 文件名 | 同名匹配 | 强 | 模型→材质（本机 48 条靠它） |
| `Sibling` | 同目录资源 | 目录前缀 | 弱 | 无人认领的资源兜底 |
| `Slot` | 资源 → 对象 | 对象表的官方模式 | 强 | 槽位证据 |

### 5.2 三类难点的处理

- **共享资源**：同名贴图/材质出现在多个包里，不合并、不跨包连边。每个包独立构图，避免「一个包的证据污染另一个包」。
- **非标准目录**：`Slot` 边连不上时，靠 `NamedBy` + `References` 走两步；仍连不上才退到 `Sibling` + 名称（T3）。
- **缺失文件**：VMT 指向的 VTF 不在包内 = 覆盖官方贴图（自包含补丁）；VMT 在、VTF 也在但 `$basetexture` 指向包外 = 引用官方贴图。这两种在现有系统里完全没区分，但它们对「这个包改了什么」意义不同。

### 5.3 混合 MOD = 多个连通分量

一个包里有 3 个互不相连的子图（模型组 / HUD 材质组 / 音效组），就是混合包。**分量数 ≥ 2 时不允许只报一个主体**——这正是现在 `Kinds` 里塞「附带:」字符串要表达的东西。

## 6. B6 综合推断

### 6.1 证据分级（按「能不能被文件名伪造」排序）

| 层 | 证据 | 为什么在这一层 | 本机例子 |
|---|---|---|---|
| T0 | MDL 内部名指向官方槽位 | 改文件名不影响内部名 | 睦月的 `v_desert_rifle-1.mdl` |
| T1 | 资源的官方路径槽位（v_/w_ 模型、官方材质目录） | 加载机制决定，作者几乎不会改 | 12 个包里的模型路径 |
| T2 | 关联推断（贴图名→VMT→官方材质） | 依赖 T0/T1 锚点，一步可达 | 48 条 VMT 的挂接 |
| T3 | 文件名 / 标题文本 | 作者随便写 | 「唐刀」「铁盆」 |
| T4 | 子串命中（现 `Dict` 的做法） | 最容易被「ammo」「laser」这类词骗 | 2 条 ammo 假阳性 |

**独立性规则**：同一个事实的多份拷贝只算一条证据。一个包里有 20 张材质都含 `shotgun`，证据仍然是 1 条，不因数量升权——这条直接针对「不能简单通过命中数量决定可信度」。

### 6.2 裁决流程（通用，不含具体对象）

```
1 收集证据（每条带 tier、来源资源、独立性 key）
2 去重：同 key 只留最强 tier
3 若存在 T0/T1：
    取最高 tier 的对象集合
    若集合内 1 个 → 已识别；≥2 个 → 混合（主/辅按分量大小）
4 否则若存在 T2：沿关联汇聚，≥2 个不同来源同指向 → 已识别；单来源 → 待复核
5 否则若只有 T3/T4：给候选，不落槽，状态=未知（附候选与理由）
6 若最强证据互相矛盾（如 T1 指 A、T0 指 B）→ 状态=冲突，保留双方，取 tier 高者为暂定
7 全程把「用了哪条证据、排除了哪条」写进结果
```

关键差异：现在第 3 步不存在（早退），第 6 步不存在（冲突被静默丢弃），第 7 步只有一个 `Trace` 字符串。

## 7. B7 结构化识别结果

```csharp
sealed class IdentificationResult {
    ObjectRef Primary;            // 可空 = 未知
    ObjectRef[] Objects;          // 混合/多主体
    string Category, Sub;         // 分类映射结果（与对象分离）
    Confidence Confidence;        // High/Medium/Low/Unknown（由 tier 推导，不打分）
    Status Status;                // Identified / Review / Conflict / Mixed / Unknown
    Evidence[] Evidence;          // 每条：tier、来源资源、命中内容、独立性 key
    Conflict[] Conflicts;         // 双方证据与未采用理由
    string[] Unresolved;          // 明确说「哪一步没走出来」
}
```

**与现有代码的兼容**：`ModItem` 的 `Subject / SubjectLevel / SubjectKey / Kinds / Trace` 全部由新结果**投影**生成，不新增第二套真相。缓存沿用 13 列格式，只追加列（老行按现有「列少了就补读」逻辑兼容），指纹改为「规则表 + 逻辑版本常量」，不再靠人肉改串。

## 8. B4 VMT 解析收益验证（真实样本）

### 8.1 统计口径

对 12 个包逐个读目录表，抽出全部 `.vmt`（81 条，单条 ≤ 256 KB），解析 `$basetexture`、patch 标记与常用参数。**全部只读，未写出任何文件到 MOD 目录。**

| 指标 | 数值 |
|---|---|
| 包数 / VMT / MDL | 12 / 81 / 16 |
| VMT 路径自带可识别词 | 32（其中 2 条是 ammo 假阳性） |
| 只能靠 MDL 贴图名挂接 | 48 |
| 谁都挂不上 | 1 |
| patch / include 型材质 | 0 |
| 含 `$color2` / `$selfillum` | 16 / 51 |

### 8.2 结论

1. **VMT 对对象判定新增 0 例。** 所有能靠 VMT 判出来的对象，路径法已经判出来了；路径法判不出的（睦月、Deep Seek 的自定义材质），VMT 也判不出，因为 `$basetexture` 指向的仍是作者自己的目录。
2. **VMT 用错地方会新增假阳性。** `ammo` 的两条命中，如果直接参与主体判定，Deep Seek（15发木狙）和睦月（SCAR-L）都会多出一个「弹药」主体。这说明「凡是资源路径都能当证据」是错的。
3. **VMT 的真实价值在三处**：关联链的中间节点（48 条）、patch 型材质的直接线索（本机 0 例，但线上常见）、意图标签（换色/发光，16/51 条带参数）。
4. 因此 **VMT 解析器降级为 P1**，排在 MDL 头解析之后。

### 8.3 扩大到 110 个包后的复核（U 盘样本）

样本：`D:\游戏内容\求生之路2各项MOD` 下全部 110 个 vpk（6.5 GB），只读。

| 指标 | 数值 |
|---|---|
| 包 / 条目 | 110 / 8515 |
| VMT 总数（目录表） | 2702 |
| VMT 实际解析（每包上限 60） | 1761 |
| 路径与 `$basetexture` 都能认出对象 | 320 |
| 只有路径能认出 | 22 |
| **只有 `$basetexture` 能认出** | **1** |
| 两者都认不出 | 1418 |
| patch / include 型材质 | 0 |

结论（比 12 包样本更硬）：

1. **`$basetexture` 对对象判定几乎零贡献**：1761 条里只有 1 条是「路径认不出、靠 basetexture 才认出」。原因是 modder 通常把 VMT 直接放在官方路径下（路径已经指明对象），自定义路径的 VMT 其 basetexture 又指向作者自己的目录。
2. **patch 型材质在这 110 个包里一次都没出现**。上一版报告把「patch 型材质」列为 VMT 的潜在价值点，样本证明：至少在本地库里，它不是主要形态，不能作为设计的主要依据。
3. **路径证据依然是最强的一层**，但有一种新的假阳性：粒子/弹道包会把武器槽名写进材质文件名——`Scattershot 4` 里的 `sniper_scout.vmt` / `sniper_military.vmt` / `smg_silenced.vmt`，路径法会读成「鸟狙 / 30发军用狙 / MAC-10」，而它其实是一个影响这些武器的**粒子包**。这类必须靠「资源类型（particles）+ 目录」压制，不能靠名字。

## 9. B5 MDL 解析：价值、成本、边界

### 9.1 实测可得信息

| 字段 | 位置 | 本机可得 | 用途 |
|---|---|---|---|
| 魔数 `IDST` | 0 | 16/16 | 完整性/格式判定 |
| 版本 | 4 | 全部 49 | 兼容性 |
| 内部名（64 字节） | 12 | 16/16，**与条目名可不同** | T0 证据 |
| 贴图表（numtextures/textureindex） | 204/208 | 68 个贴图名 | 关联 + 谱系 |

实测样本：`models/v_models/v_desert_rifle-1.mdl` → 内部名 `v_models\v_desert_rifle.mdl`；`models/weapons/melee/v_katana.mdl` → `v_katana.mdl`。

### 9.2 价值判断

- **高**：内部名抗改名。这是唯一一条「作者改了文件名也骗不过」的线索，且读取成本只有几百字节。
- **中**：贴图表能建立模型→材质关联（本机 68 个贴图名里 48 条 VMT 靠它挂接）。
- **低且危险**：贴图名当对象证据。4/6 命中是假阳性，且贴图会继承原模型（铁盆案例）。

### 9.3 成本与风险

- 成本：读头部 + 贴图表偏移，几十行代码；不需要解析骨骼/动画/顶点。
- 风险：偏移写错会读到垃圾 → 用版本号白名单（44/48/49）+ 边界校验 + 长度上限，失败即返回空。
- **明确不做**：不解析 bodypart/mesh/动画，不读 VVD/VTX 内容。

| MDL 贴图名总数 | 2201 |
| 贴图名命中现有词表 | 105 |

改名样本（全部真实）：

| 条目名 | 内部名 | 说明 |
|---|---|---|
| `tiepen.mdl` | `v_shotgun_chrome.mdl` | 条目名是拼音，**零信息** |
| `wmcapple.mdl` | `w_eq_medkit.mdl` | 条目名随手起，**零信息** |
| `v_huntingriflefix.mdl` | `v_huntingrifle.mdl` | 加了后缀 |
| `v_rifle_ak47_1.mdl` / `v_rifle_ak471.mdl` | `v_rifle_ak47.mdl` | 加序号 |
| `v_desert_rifle-1.mdl` | `v_desert_rifle.mdl` | 加 `-1` |
| `v_smg1.mdl` | `v_smg.mdl` | 加序号 |

前两行是关键：**条目名里没有任何对象词**，现有路径法只能落到「未归类」，而内部名直接给出槽位。这 14 条不是边角案例，是 8.3% 的模型。

同时对「贴图名当证据」给出了更强的否证：105 条命中里大量是

- `att_ammo_762n` / `m_mtl_ammo_sat_762n` → 「弹药」（弹匣贴图，不是弹药包）
- `weapon_vm_ar_scharlie_v20_pistolgrip` → 「手枪」（AR 的握把）
- `MT_AthenaPrecision_Chassis_Rifle` → 「M16」（Athena 的枪身）
- `MT_SVD_Battle_Rifle_body` → 「M16」（SVD 枪身）

这些全是**部位名**，指向的不是对象。结论：贴图名只能用于关联，不能进证据池。

## 11. 安全与性能

| 项 | 约束 |
|---|---|
| 读模式 | 只读打开，不写 MOD 目录；解析器只收内存字节 |
| 单文件上限 | VMT 256 KB / MDL 2 MB / VTF 头 64 KB / PCF 1 MB |
| 单包预算 | 解析单元 ≤ 200 个，累计读取 ≤ 8 MB，超限记 Skipped 并继续 |
| 异常隔离 | 每个解析器独立 try/catch；坏文件返回空，不冒泡 |
| 执行 | 不执行任何 MOD 内容；NUT 只做静态文本匹配 |
| 时间 | 单包解析目标 ≤ 50 ms（C# 实现；Python 原型 12 包全量 < 3 s，未优化） |
| 内存 | 逐条解析后即释放，不保留原始字节 |
| 缓存 | 只缓存解析结论与证据摘要，不缓存原始文件 |

实测：12 个包（含 161 MB 的大包）全量读目录表 + 抽取 81 个 VMT + 16 个 MDL 头 + 68 个贴图名，总耗时 < 3 秒（Python 原型，未优化）。
