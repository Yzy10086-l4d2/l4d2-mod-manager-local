# C1.6 官方资源过滤补齐、关系分层与多主体位置映射

**性质**：只读 + Shadow。正式分类、用户分类、分类树、缓存、识别规则均未改；未合并任何 MOD。
**样本**：110 个 vpk；官方基准 = 游戏 `pak01_dir.vpk`（17 118 名）；位置表 = 仓库 `Positions.cs`（只读解析）。

---

## 0. 结论

1. **官方资源改为双证据 + 三态**：`pak01NameMatch`（名字命中）、`officialPathDomainMatch`（路径域命中）分开记录，状态为 official / official-name / candidate-domain / unknown，可追溯，不合并成一个 boolean。
2. **过度关联从 2 例降到 0**：特感高亮、彩色高亮特感不再被判为 possible-component；原因与证据在 JSON 的 `officialEvidence` 里可查。
3. **关系按语义分层输出**：组件关系 / 来源关系 / 技术依赖 / 未知关系，层级只用于展示，不改变任何判定。
4. **多主体位置映射可用**：110 个主体中 92 个映射到现有位置表（candidate），18 个无候选（石头、concrete_chunk*、音效套装等）；映射只作候选，不回写分类。
5. **40 个人工样本**：一致 31（C1.5 为 29），过度关联 0（C1.5 为 2），保守 9（未变）。
6. **收益有边界**：分层的价值是可读性，官方过滤的价值是删除假关联；两者都不产生新的确定关系。

## 2. 官方资源识别设计

两种独立证据，分别记录：

| 证据 | 来源 | 含义 | 单独能定官方吗 |
|---|---|---|---|
| pak01NameMatch | 游戏 pak01_dir 目录表 | 这个名字游戏自带 | 能 |
| officialPathDomainMatch | 资源路径落在 `models/、materials/models/、sound/weapons|player|npc/、materials/particle/、particles/` | 这个位置通常是官方资源域 | **不能**，只给 candidate-domain |

状态：

- 两者都真 → `official`
- 只有名字 → `official-name`
- 只有路径 → `candidate-domain`
- 都假 → 不进 officialEvidence，按自定义资源处理

**用途限制**：官方资源只用于「排除归属推断中的共享名」，不删除资源事实；`resourceTypes` 计数、影响面、Trace 照旧。冲突时（名字假、路径真）按 candidate-domain 处理——只排除 same-origin，不排除 dependency。

## 3. 过滤前后对比

| 指标 | C1.5 | C1.6 |
|---|---:|---:|
| 官方名被过滤 | 183 | 231（其中 pak01 名字 183、路径域新增 48） |
| component | 2 | 2 |
| possible-component | 3 | **0** |
| same-origin | 35 | 34 |
| dependency | 3 | 3 |
| unknown | 67 | 71 |
| 多主体包 | 2 | 2 |

变化解释：

- possible-component −3：特感高亮、彩色高亮特感、1 个同目录组合被路径域证据排除。
- same-origin −1：1 对共享名落在官方路径域，被降为 unknown。
- unknown +4 = 上述 3+1。
- dependency 不变：A 级证据仍只用 pak01 名字，不引入路径域，避免误删真实依赖。

## 4. 关系分层展示

JSON 新增 `ownership.layer`，值域：组件关系 / 来源关系 / 技术依赖 / 未知关系。每层内保留 A/B/C 证据与 detail，不隐藏 unknown。

示例（⑨ 1 号）：

```
"ownership": {
  "status": "component",
  "layer": "组件关系",
  "relations": [
    {"to":"2 [東方Project]⑨…","type":"dependent","strength":"A","detail":"对方 PCF 引用本包 5 个材质名"},
    {"to":"3 [東方Project]⑨…","type":"name-similar","strength":"C","detail":"同目录 + 名前缀 12 字"}
  ]
}
```

展示规则（写进报告，不改 UI）：层名只是标题；组件关系里 `component` 与 `possible-component` 必须分开显示；依赖层不得出现"同套"字样。

## 5. 多主体位置映射

结构：`subject.objects[].location = {candidate, status}`，status ∈ candidate / no-candidate / unknown-subject。

**特感圣诞帽**（10 个主体）：

| 主体 | 状态 | 位置候选 |
|---|---|---|
| 通用 | identified_from_formal | 特感 / 通用 |
| witch | candidate_from_model | 特感 / Witch |
| spitter | candidate_from_model | 特感 / Spitter |
| smoker / jockey / hunter / hulk / charger / boomette / boomer | candidate_from_model | 各自位置 |
| （共 10） | — | 10/10 有候选 |

**大肥鱼石头**（8 个主体）：

| 主体 | 状态 | 位置候选 |
|---|---|---|
| 石头 | identified_from_formal | 无（位置表没有"石头"） |
| concrete_chunk01a / concrete_spawnchunk001a~f | candidate_from_model | 无（位置表无对应行） |

结论：映射只回答"可能对应哪个位置"，不回写分类；石头系列 8 个主体全部无候选，暴露的是位置表缺行，而不是识别错误。

## 8. 新增误判与失败案例

1. **无新增过度关联**；但 unknown 从 67 升到 71，属于"用保守换准确"，需人审确认是否过严。
2. **路径域证据可能误伤**：如果作者把自定义材质放在 `materials/models/` 下（常见），会被判 candidate-domain 而排除同源证据。本次影响 1 对（same-origin 35→34）。
3. **位置映射失败 18 例**：石头/混凝土块、音效套装等，位置表本身没有这些行。
4. **多主体仍是英文模型名**：映射成功的是因为位置表英文名恰好一致；中文展示需再接一层。
5. **candidate-domain 的阈值未验证**：路径域清单是我按游戏常见目录列的，没有做过误伤统计。

---

## 9. 无法解决

- 模型件与材质件的连接（霓虹）：需要 MDL 贴图表或 VMT `$model`，本阶段禁止。
- pak01 名称缺口（部分官方材质名不在目录表）：路径域只补了一部分，无法证明的一定要保持 candidate。
- "同套"的最终确认：本阶段只能到 component（引用+同目录），跨目录的真实套装（如同作者分卷发布）无法证明。

## 11. 是否进入下一阶段

建议：**停止扩展，先整理现有成果**。理由：

1. 三项任务都已落地并有可复核数据，边际收益递减。
2. 剩余问题（模型↔材质、真实套装确认）都需要被本阶段禁止的解析能力，继续加规则只会增加复杂度。
3. 下一步的价值在"人工核验 + 正式接入评估"，不在新功能。

若必须继续，唯一值得做的是：把 71 个 unknown 做 30 条人工抽样，确认保守阈值是否合理。

## 12. 六个问题的回答

1. 官方过滤有泛化价值：是。它删掉了 2 例假关联，且规则来自游戏自带资源表，不是关键词。
2. 关系分层解决语义混淆：是。层名与状态分离，依赖不会被读成同套。
3. 多主体映射有用：有限。92/110 能映射，18 例暴露的是位置表缺口。
4. 新误关联：0 例；但 unknown 增加 4 例，属于保守代价。
5. 有足够证据进入下一阶段吗：做"接入评估"有；做"继续加模型"没有。
6. 建议：停止扩展模型，转入人工核验与接入评审。
