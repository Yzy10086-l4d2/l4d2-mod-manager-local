# C1 统一资源描述与资源关系知识模型
## 设计与真实样本验证

**性质**：只分析、设计、验证。未改生产代码、规则表、分类树、用户配置与缓存；未改动任何 MOD 文件。
**对象仓库**：`_本地版源码`（main，HEAD 75a414b）。
**样本**：U 盘 110 个 vpk / 8515 条目 / 2702 条 VMT / 177 个 MDL，全部只读；实验代码在仓库外 `_probe`。

---

## 0. 结论

1. **当前系统认不出资源，是因为它从头到尾只拿到「路径字符串」。** `Vpk.Walk` 逐条回调路径后把 18 字节元数据（大小、归档号、偏移）直接跳过（Mods.cs:890），识别层只拿到名字；全流程唯一的文件内容是 addoninfo 标题（Mods.cs:930）。
2. **最少要补的通用能力是一样：资源类型证据 + 类型否决权。** 不需要先建大知识库。实测 110 个包里有 7 个「纯粒子包」，其中 2 个被现行规则判成了具体武器（§6.3）：`4 Scattershot…4.vpk` 被路径里的 `sniper_scout.vmt` 带到「鸟狙」，而它实际是 105 个 pcf 的第三人称特效包。
3. **资源关系确实能提供路径法拿不到的信息**，但方向要说准：不是「认出更多对象」，而是「知道这个资源属于谁」和「知道这个名字是主体还是影响面」。实测 48/81 条 VMT 只能靠「MDL 贴图表 ↔ 同名 VMT」挂到模型上。
4. **防误传播的办法是分层而不是加规则**：直接引用（VMT→贴图）＞ 结构身份（MDL 内部名）＞ 槽位路径 ＞ 类型上下文 ＞ 名称文本；高层的「类型结论」对低层的「名字结论」有否决权。
5. **客观测量方式**：用「现行规则输出」对「人工核验子集」算三率（正确/错误/未知），不看整体准确率。本语料可核验 9 类共 12 个案例，现行错 2、新方案改对 2，其余 108 个包结论不变。
6. **该保持未知的**：只有贴图没有 VMT 与模型、只有 pcf/脚本、纯喷漆、HUD 屏幕材质——本语料 22/110（20%）。
7. **最小可验证改动**：只做「资源类型 + 类型否决」这一条，就能修掉 §6.3 的两例，且不动任何现有判定路径。

## 1. 任务 1：现有架构复核（逐处核对源码）

### 1.1 资源数据在哪采集

| 阶段 | 位置 | 拿到什么 | 丢掉什么 |
|---|---|---|---|
| 读目录表 | `Vpk.Walk / WalkBuffer` Mods.cs:762 / 857 | 每条路径（小写）+ 预载字节 | **18 字节元数据被跳过**（Mods.cs:890）：大小、CRC、归档号、偏移 |
| 分拣 | `Scan.Feed` Identify.cs:270 | 5 个桶：模型名、HUD 图标名、音效目录、材质路径、布尔标记 | 路径层级被压成一个字符串；材质只留前 40 条（Identify.cs:321）；Assets 超 4000 直接清空（Identify.cs:299） |
| 判定 | `Scan.Finish` Identify.cs:360 | 一个 Subject、一个 Level、一个 Key、一个 Kinds 串 | 多对象只剩「附带:」，冲突无处存 |
| 转存 | `AddVpk` Catalog.cs:1205-1215 | 把 Result 的 10 个字段拷进 ModItem | 证据只留一句 Trace 文本 |
| 归档 | `Modify`（Add，Catalog.cs:1300） | Fp 包指纹 + 人工覆盖 | — |

### 1.2 信息在哪一步丢失

1. **文件大小**：目录表里有，跳过不读。大小是「同一套资源」与「损坏包」的低成本信号，现在完全没用。
2. **资源类型**：只有扩展名字符串；没有「这个 VMT 是粒子材质还是模型材质」的概念。这是 §6.3 两例误判的直接原因。
3. **引用关系**：VMT 的 `$basetexture` 从未被读（除本阶段实验外），MDL 的贴图表从未被读。
4. **多对象**：`Finish` 只输出一个 Subject，其余拼进 `Kinds` 字符串（Identify.cs:500 附近）。
5. **失败与未知**：`Analyze` 异常返回空 Result，与「没有可识别资源」同形（Identify.cs:549-552）。

### 1.3 分类入口、规则、缓存、树的关系

```
Catalog.ScanMods (790)
  → AddVpk (1193) / 压缩包 (868) / 游戏目录 (1038) / 工坊 (1106)
      → Classify (1320)            ← 目录规则 + ClassifyByPaths (1027)
      → AnalyzeCached (1330)       ← 缓存 identify-cache-<指纹>.tsv
      → RefineBySubject (1225)     ← 用 Subject 覆盖 Cat/Sub
      → Add (1300)                 ← Fp + CatPrefs.ApplyTo (302)
Catalog.ApplyCats (1579)           ← 人工大类覆盖 (1584)
CatTree.SlotIndex.Build (43)       ← 名字清洗 + 聚槽 + 未归类
```

四者关系是**单向且互相打补丁**：Classify 先定大类 → 识别再定对象 → RefineBySubject 拿对象回头改大类 → 树层再洗一遍名字。任何一层判错，后面的层只能补救，不能证伪。

### 1.4 重复结构与隐式优先级

| 类型 | 具体 | 位置 |
|---|---|---|
| 重复结构 | `Result` / `ModItem` / `ModGroup` 各存一份 Subject、Kinds、Trace | Identify.cs:14、Core.cs:13、Catalog.cs:26 |
| 重复判定 | `Catalog.Classify` 与 `ClassifyByPaths` 各定一次大类 | Catalog.cs:1320 / Identify.cs:1027 |
| 重复规则 | medkit/painpills 在 `Dict` 与 `ClassifyByPaths` 各一份；spas 三处 | Identify.cs:47 / 1130 / 562 |
| 重复代码 | 三个识别入口各抄一遍字段赋值 | Catalog.cs:869 / 1040 / 1107 / 1205 |
| 隐式优先级 | `Dict` 表序即优先级；`modelOrder` 的 v_ 优先；`ClassifyByPaths` 15 个早退出口；`RefineBySubject` 的 pkgLevel 例外 | 各处 |

### 1.5 可复用与扩展障碍

**可复用**：`Positions` 83 行（对象名/别名/中英名，已是半个知识库）、VPK 解析器与 zip/rar/7z 支持、`Fp` 包指纹、`Level + Trace` 的证据雏形、`--recogself / --idcheck` 验证设施。

**扩展障碍**：

1. `Result` 是扁平结构，加任何新证据都要在 6 个地方同步改。
2. `RefineBySubject` 是「事后补丁」，新增证据只能再打一个补丁，补丁之间互相不知道。
3. 缓存 13 列固定，只追加不重构，扩展要一直背兼容。
4. `SlotIndex` 在展示层做名字清洗（SplitKind / Vague / Concrete），反过来影响语义——同一个包在「识别明细」和「树上」可能不是同一个名字。

## 2. 任务 2：统一资源描述

### 2.1 字段逐个评估

| 字段 | 必要性 | 用途 | 事实/解析/推断 |
|---|---|---|---|
| 路径 | 必须 | 槽位证据、关联、去重 | 事实 |
| 文件名 | 必须（已是路径的一部分） | 名称证据 | 事实 |
| 扩展名 | 必须 | 资源类型的第一层 | 事实 |
| **资源类型** | **必须（当前缺失）** | 决定「名字能不能当主体证据」 | 解析/推断 |
| 文件长度 | 需要 | 损坏检测、同套判断 | 事实 |
| 解析状态 | 必须 | 区分「读不了」和「没有信息」 | 事实 |
| 内部标识 | 按类型可选 | MDL 内部名、VMT shader、VTF 尺寸 | 解析 |
| 对象候选 | 推断层，不属于资源 | 推理输出 | 推断 |
| 关联关系 | 必须 | 连接资源与对象 | 推断（带强度） |
| 识别依据 | 必须 | Trace 与复核 | 推断 |
| 数据来源 | 必须 | 区分「读到」与「猜到」 | 事实/推断 |
| 冲突标记 | 必须 | 不静默丢弃反证 | 推断 |
| 未知标记 | 必须 | 允许不知道 | 推断 |

**不要的字段**：不做「置信分数」（用等级 + 依据即可）；不做「资源权重」（权重写在证据层，不写在资源上）。

### 2.2 结构草案

```csharp
sealed class RawAsset {              // 事实：只读，不做判断
    string Path; string Ext; long Size;
    string Container; string Inner; int ArchiveIndex;
    bool Readable; string ReadError;
}
sealed class ParsedAsset {           // 解析：由资源自己说的
    RawAsset Raw; AssetKind Kind;    // Model / Material / Texture / Sound / Particle / Script / Map / Ui / Anim / Other
    ParseStatus Status;              // Ok / TooBig / BadFormat / Unreadable / Skipped
    string InternalId;               // MDL 内部名
    string Shader; string BaseTexture; bool IsPatch;   // VMT
    string[] TextureNames;           // MDL 贴图表
}
sealed class Relation {              // 关系：必须带强度和理由
    string From, To; RelationKind Kind; RelationStrength Strength; string Because;
}
enum EvidenceTier { T0_Structural, T1_SlotPath, T2_Reference, T3_TypeContext, T4_Name }
sealed class Evidence { EvidenceTier Tier; string Source; string Fact; string IndependenceKey; }
sealed class ModIdentification {     // 决策：与展示分离
    ObjectRef[] Subjects; string Category, Sub;
    Confidence Confidence; Status Status;       // Identified / Mixed / Conflict / Review / Unknown
    Evidence[] Evidence; Relation[] Relations; string[] Affected; string[] Unknowns;
}
```

**MDL 内部名**放在 `ParsedAsset.InternalId`，只产生 T0 证据与去重 key，不直接写 Subject（B1 已验证包级增益为 0）。

## 3. 任务 3：资源关系模型

### 3.1 哪些关系是「读过文件就知道」的

| 关系 | 来源 | 强度 | 本语料实测 |
|---|---|---|---|
| 材质 → 贴图 | VMT `$basetexture` | 直接 | 1761 条 VMT 中 343 条能对上对象，1 条只有 basetexture 能识别 |
| 模型 → 材质 | MDL 贴图表 ↔ VMT 同名 | 结构 | 81 条 VMT 里 48 条靠它挂上（12 包样本） |
| 模型 → 对象 | MDL 内部名 = 官方槽位模型名 | 结构 | 172 个模型可读，14 个与条目名不同，0 冲突 |
| 材质 → 对象 | VMT 路径是官方材质路径 | 槽位 | 32/81 条 |
| 音效 → 对象 | `sound/weapons/<对象>/` | 槽位 | 仅 weapons 目录 |

### 3.2 只能靠弱证据推断的

同目录、名字相似、标题提到。**规则：名字相似不建立关系**，只建立「候选」，且候选永不升级为 Subject（最多进 Affected 或 Unknowns）。

### 3.3 六问六答

1. **怎么区分确定与猜测**：关系带 `Strength { Direct, Structural, Conventional, Nominal }`。Direct/Structural 可传递，Nominal 不传递。
2. **怎么防错误传播**：只允许沿 Direct/Structural 边传播；传播不超过 2 跳；类型守卫（Particle 节点不得传播成武器主体）。
3. **一份资源关联多个对象**：允许多边，但每个对象各记一条证据；主体选择按 §5 的裁决，不做多数投票。
4. **完全无法建立关系的资源**：进 `Unknowns`，并注明「无模型、无引用、无官方路径」。
5. **同名但不是同一物**：只在同一包内、且名称完全相等时建立 Structural 边；跨包不连边（避免共享资源污染）。
6. **共享资源**：同一贴图被多个 VMT 引用时，是该包的内部事实，不跨包合并。

## 4. 任务 4：游戏知识模型

| 问题 | 结论 | 理由 |
|---|---|---|
| 对象与资源类型是否分离 | **必须分离** | 对象是「铁喷」，资源类型是「模型/材质/粒子」；混在一起就会出现「粒子材质 → 武器」这种推导 |
| 分类树是否只是展示层 | **是** | 树只消费 `(Category, Sub, Subjects)`，不参与推理；本阶段不动树 |
| 同一对象多种资源形式 | 允许 | 铁喷 = v_ 模型 + w_ 模型 + 材质 + 音效 + HUD 图标，都指向同一 ObjectId |
| 一个 MOD 多主体 | 允许 | 按连通分量给 Subjects[]，主/辅分离 |
| 允许未知 | 必须 | Subject 可空、类型可空、关系可空，三者独立 |
| 如何避免大量路径关键词 | 把「官方资源模式」写进对象记录（不是散落的匹配表），匹配算法对所有对象一致 | 现有 `Positions` 已是对象表，只缺「官方资源模式」这一列 |

## 5. 任务 5：证据聚合与推理

### 5.1 分层

| 层 | 证据 | 能否决定主体 |
|---|---|---|
| T0 | MDL 内部名 == 官方模型名 | 能（最强） |
| T1 | 资源路径 == 官方资源路径 | 能 |
| T2 | 资源内容引用官方资源（$basetexture、贴图名） | 能，需 ≥2 条独立 |
| T3 | **资源类型组合**（pcf + particle 材质 + 无模型 → 特效） | **不是对象证据，是类型否决权** |
| T4 | 文件名 / 标题 / 目录名 | 不能，只能给候选 |

### 5.2 类型否决（本次设计的关键一条）

若 T3 判定包的主要资源是特效/音效/喷漆：
- T4 里的武器名只能进 `Affected`；
- 不得据此设置 Subject；
- 若同时存在 T0/T1 的模型证据，则模型证据照常胜出。

这条直接修掉 §6.3 的两例，而且**不需要新增任何对象规则**。

### 5.3 裁决伪代码

```
evidence = collect(assets)                 // 去重：同 IndependenceKey 只留最高 tier
typeGuard = classifyAssetMix(assets)       // Model-bearing / Particle-only / Sound-only / Ui-only / Texture-only

if typeGuard == Particle-only or Sound-only or Spray-only:
     subject = []; affected = namesFromT4()
     status = Identified(type) 或 Unknown
else:
     strong = evidence where tier in (T0,T1)
     if strong: subject = argmax(tier), 同 tier 多对象 → Mixed
     elif T2 独立证据 >= 2: subject = 逐条汇聚
     else: subject = []; status = Unknown，附候选

若出现 tier 冲突（T0 指 A、T1 指 B）：status = Conflict，两者都保留，不自动覆盖
```

### 6.3 两个改判案例的完整证据

**案例 2：`4 Scattershot 散射步枪（SPAS 二代连喷）4.vpk`**（201 条）

- 实际构成：pcf 105、txt 55、vtf 18、vmt 18、jpg 2、xlsx 1、backup 1；目录集中在 `particles/`、`for_modders/particles/`、`materials/3ptesturik/`；**无 models、无 sound**。
- 现行结果：枪械 / 狙击枪 / 鸟狙（基线原文）。
- 现行依据：18 条 VMT 的路径是 `materials/3ptesturik/sniper_scout.vmt` 等，落进 `Mats` 桶，`Lookup` 命中 `sniper_scout` → Subject=鸟狙；随后 `RefineBySubject` 把大类从杂项改回枪械。
- 新方案读到的事实：这 18 条 VMT 的 `$basetexture` 全部指向 `particle/3PtestUrik/*`；包内有 105 个 pcf、路径段 `particles`。
- 关系：特效资源 → 命名指向 5 个武器槽（鸟狙、30发军用狙、AWP、MAC-10、MP5），但没有任何模型或官方材质路径。
- 判定：类型 = 粒子特效包；主体未知；影响面 = 5 个武器。
- 不确定：作者是否附带枪械皮肤（无 models 条目，判为否）。
- 相对现行：从「鸟狙」改为「特效 + 影响面」，**错→对**。

**案例 3：`3 Scattershot…3.vpk`**（44 条）

- 构成：materials/particle/halo 33 条 + 1 个 pcf；无 models。
- 现行结果：枪械 / 一代连喷；依据只能是标题里的「连喷」（`GuessFromText`，Identify.cs:606）。
- 新方案：类型 = 粒子特效；T4 的「连喷」不进 Subject；状态 Unknown（附「可能影响霰弹枪特效」）。
- 相对现行：从「确定但错」改为「不确定但诚实」。

| C1.4 | 结构化结果 + 投影（旧字段保留） | C1.3 | 中 | idcheck 零改判；缓存兼容 |
| C1.5 | 混合/多主体输出（连通分量） | C1.4 | 中 | 特感圣诞帽输出 6 个物种清单 |
| C1.6 | 人工核验子集（30–50 条）与三率统计 | C1.5 | 低 | 有可复现的准确率口径 |

**不做**：VMT 内容当对象证据（实测 1/1761）、MDL 贴图名当对象证据（4/6 假阳性）、单独的内部名识别器（包级 0 增益）。

## 9. 七个验收问题的直接回答

1. **为什么理解不了资源**：只读路径，不读内容；资源类型只有扩展名，没有「这是什么」的概念。
2. **最少要加什么**：资源类型判定 + 类型否决权。其余（关系图、结构化结果）是配套。
3. **关系能否提供路径法没有的信息**：能，但主要在「归属」和「影响面」，不是「新对象」。
4. **怎么防错误关联**：关系带强度，只沿 Direct/Structural 传播，≤2 跳，粒子节点不得传播成武器主体。
5. **怎么客观测量**：人工核验子集 + 三率（正确/错误/未知），保留错误案例；不看整体准确率。
6. **哪些该保持未知**：无模型、无 VMT、无官方路径的包（本语料 20%）。
7. **有没有最小改动**：有，C1.1+C1.2 两步即可修掉本语料的两例误判，不动其他任何判定。
