## 0. 结论摘要

1. **链路是完整的，能跑**：VPK 目录表 → 四级证据（模型 / HUD 图标 / 音效 / 材质）→ 位置名 → 大类小类 → 槽位 → 树。本地编译一次通过（§5.1）。
2. **「识别结果」不是一个模型，是一个字符串加一个字符串**：`ModIdentify.Result` 只有 `Subject`（名字）和 `Level`（依据级别，取值为「模型 / HUD图标 / 音效 / 材质 / 标题 / 文件名 / 地图 / 平台 / 整套」）。没有置信度枚举，没有状态（已识别 / 未知 / 待复核 / 混合），没有证据列表，没有结构化冲突。多个对象的并列表述被拼成 `"附带:A/B"` 塞进 `Kinds` 字符串（`Identify.cs:28`、`Finish()` 内拼接），下游只能原样显示，无法判定。
3. **规则分散在 11 处**（明细见 §3）。同一概念重复定义已经不是隐患而是事实：`medkit / painpills / adrenaline` 在 `Dict` 和 `ClassifyByPaths` 各写一份；`spas` 在 `Dict`、`AliasKeys`、`UpgradeShotgunByText` 三处各写一份；「近战 / 投掷物 / 弹药升级」既是 `Positions.Sub` 又是 `CatTree.CatOfSub` 的映射结果。
4. **缓存失效靠人肉改字符串**：`RuleFingerprint()` 只哈希 4 张规则表加位置表，`rules:2026-11-22a` 这行（`Identify.cs:877`）要人手改。`ClassifyByPaths`、`UpgradeShotgunByText`、`IsUiAssetPath`、`MatUsable` 的逻辑改动全部落在这个盲区里。
5. **两条链上的「包身份」不是同一个**：识别缓存以 `RelPath` 为键（`Identify.cs:1330`），人工归类以包内容指纹 `Fp` 为键（`Catalog.cs:1283`）。同一个包改名后，人工结论认得出来、识别缓存认不出来。
6. **匹配方式只有一种，优先级就是表序**：`Dict / AliasKeys / InfectKeys` 全部是 `IndexOf` 包含匹配，没有精确 / 路径段 / 前缀之分。`"shotgun"` 只有当 shotgun_chrome、shotgun_spas 排在它前面时才不出错，表序即优先级，代码里没有显式优先级字段。`Positions.Canonical` 的归一也是别名精确查表，查不到就原样透传，悬空名会一路带到树上。
7. **有一处实打实的漏判**：`AddVpk` 是散装 vpk 的主路径，缺了另外两条路径都有的「幸存者」回落保护（`Catalog.cs:1205` 对 `1045` / `1111`）。八人包在散装路径上仍会被 `Analyze` 给出的单一 Subject 覆盖。
8. **测试是内存自检加基线 diff**，不是单元测试：`--recogself` 约 30 条断言（`Catalog.cs:2191`），`--dumpid / --idcheck` 拿 152 行基线比「改判」。没有独立测试工程、没有 CI。基线里大量条目的「识别结果」为空，按任务书第二条禁止事项，不能当真值用。

一句话：**结构上「能认」，但认出来的东西不能自证、不能复核、规则改动不能自证生效**。任务书要解决的六个问题，本地版在「用户数据不被自动结果覆盖」这一条上已经做对了；其余五条都在。

数据流上有两个要点：

- **Classify 在 Analyze 之前跑**。目录证据先定大类，包内证据后到，靠 `RefineBySubject` 事后对齐。所以「谁纠正谁」不是设计出来的，是执行顺序决定的，注释里写满了 2026-11-19 / 11-20 / 11-21 的补丁。
- **识别结果和位置表是两套名字，靠 `Positions.Canonical` 收口**。`Result.Subject` 的 setter 里做归一（`Identify.cs:19`），任何走 setter 的写入都会被规范化。

### 2.2 识别层：四级证据 + 三条兜底

`Scan.Feed()` 只认这些路径，其它一律丢弃：

| 桶 | 路径条件 | 用途 |
|---|---|---|
| Mdls | `*.mdl` | 最硬证据，换的就是它 |
| Huds | `materials/vgui/hud/icon_*.vtf` | 单件 HUD 图标 |
| Snds | `sound/weapons/<对象>/` | 音效归属 |
| Mats | `materials/**`，剔除 particle/decals/vgui/sprites/effects/detail | 弱证据，前三级都没中才用 |
| 其它 | `maps/*.bsp`、`scripts/*`、`particles/*` | 决定影响面与「是不是地图」 |

`Finish()` 的判定顺序（顺序即强弱，写在注释里）：

1. `maps/*.bsp` → `Level = "地图"`，Subject 最终清空（地图包里自带枪模不算「换枪」）。
2. 模型名查 `Dict`，**v_ 前缀优先于 w_**（`modelOrder`）。这一步的注释解释得很清楚：世界模型多个变体共用，视角模型才指名是哪一个。
3. 模型名认不出时，看 `models/survivors/<人名>/` 一级目录；命中 1 人给那个人，≥2 人给「幸存者」。
4. 模型级 Subject 取「出现次数最多」，其余拼成 `Kinds += "附带:A/B"`。
5. HUD 图标名、音效目录名依次补位。
6. 材质：先按 `materials/models/survivors/<人名>/` 分区判人，再用 `Lookup` 通用匹配。
7. 包内 infected 资源覆盖 ≥2 种特感 → Subject 改「通用」（地图包除外）。

在此之上叠两条文本兜底：

- `GuessFromText`（`Identify.cs:606`）：**仅当 Subject 为空**时，用文件名 → addoninfo 标题/描述对 `AliasKeys`。短 ASCII 关键词用词边界正则，长关键词（含中文）用包含匹配。
- `UpgradeShotgunByText`（`Identify.cs:562`）：**仅在 Level 不是「模型」且已判到霰弹枪某格**时，用文件名/标题强制改判（SPAS → 二代连喷等）。这是全套规则里唯一「弱证据覆盖已有结论」的地方。

### 2.3 分类层：目录规则 + 内容规则

`Catalog.Classify` 先按所在目录判（三方地图 / 人物 / 喷漆 / 医疗物品 / 特感 / 物品储藏库），均不命中才走包内容。`ClassifyByPaths` 的判定顺序（`Identify.cs:1027` 起，共 27 个 `return true` 出口）：

地图(bsp) → 战役素材卷(missions/*.txt) → 天空盒/地面细节 → 人物(按人数 1/2/≥3) → 非普通感染者 → 特感通用(≥2 种) → 特感 → 药品 → 枪械/近战/投掷物/弹药升级 → 无 .mdl 时：纯喷漆 → 单枪 HUD 图标 → 整套 UI → 弹道 → 特效 → 音效 → 脚本。

### 2.4 归一与位置表

`Positions` 是唯一位置源，83 行：小分类 / 显示名 / 英文名 / 别名。`Order()` 供树排序，`Canonical()` 做名字归一，`Suggest()/Hint()` 给未归类提候选，`Audit()` 检别名撞车。**这是现有代码里设计最干净的一处**，任务书「单一事实源」的目标在这一层已经实现，问题在识别层还留着副本。

### 2.5 缓存

| 项 | 现状 |
|---|---|
| 文件 | `<CfgDir>/_本地版记录/identify-cache-<8位指纹>.tsv` |
| 键 | `RelPath`（相对库根路径） |
| 失效 | 值里带 stamp（文件长度与修改时间拼接）；不一致就重算 |
| 列 | 13 列：relPath, stamp, Subject, Level, Key, Kinds, Only1P, Entries, base64(Assets), AnimOnly, Title, Author, Trace |
| 指纹 | `"rules:<手写串>"` + Dict + AliasKeys + InfectKeys + SurvivorDirs + Positions |
| 写盘 | 后台线程 + 整份换名（`Core.WriteAllTextAtomic`），旧指纹文件自动删 |
| 空结论 | 照存照用（7z 读不出的包，避免每次启动重解） |

### 2.6 用户数据与人工覆盖

`<PkgDir>/方案树分类.ini`：`cat= / slot= / mod=<key> / fp=<指纹> / suborder= / posorder= / slotsub=`。优先级 `mod=`（路径键）> `fp=`（包指纹）。`CatPrefs.ApplyTo` 在 `Add` 时把人工结论写回 `it.Cat / it.Sub`，树上再查一次。

这条边界是对的：**自动识别写 `Subject`，人工只写 `Cat / Sub` 和 ini，两边不共字段**。任务书「自动结果不得覆盖用户明确设置」这一条，现状满足。

### 2.7 可解释性的出口

- 树上未归类行的 ToolTip 附「识别经过」（`CatTree.cs:3805`），内容就是 `Trace`，形如 `规则:模型名 · 命中:pumpshotgun`。
- `Catalog.DumpIdentify` 导出 `识别清单.tsv`（9 列，含归组依据与证据链）和 `识别明细.tsv`（9 列，含每个部件的 Trace）。这是现在唯一的「证据」形态：一句话，不是可查询的结构。

## 4. 问题清单

风险等级：P0 = 直接影响识别正确性或数据安全；P1 = 影响可解释性/可维护性，会导致后续改动出错；P2 = 工程卫生。

### P0-1 识别结果缺模型：无置信度、无状态、无冲突、无证据列表

- **表现**：识别结论 = `Subject` 字符串 + `Level` 字符串。`Level` 混用了「证据强度」（模型/材质/音效）和「类别」（地图/平台/整套）两种语义。
- **位置**：`Identify.cs:14-40`（Result 定义）、`Identify.cs:500-530`（附带拼接）、`Core.cs:25-35`（ModItem 转存字段）。
- **原因**：历史演进中每遇到一个误判就加一个布尔/字符串，没有回头抽象。
- **影响**：任务书阶段 1、3、6 全部无法开工；「证据不足时允许未知/待复核」现在只能落到「未归类」一档，与「认不出」不可区分；多主体只能拼字符串。
- **建议**：按阶段 1 建 `IdentificationResult { Subject[]; Category; Sub; Confidence; Status; Evidence[]; Conflicts[] }`，先做等价投影，不改判定。
- **验证**：新增投影往返测试（旧 Result → 新模型 → 旧字段，逐字段相等）。

### P0-2 规则分散 11 处，同一概念多处定义

- **位置**：见 §3 表与重复清单。
- **原因**：没有统一规则入口，规则随具体误判就近写。
- **影响**：改一处不改另一处 → 结论互相抵消；新增一种枪要改 3 个文件；任务书「单一事实源」不成立。
- **建议**：阶段 2 建 `RuleTable`（规则行：匹配方式、模式、对象、证据级、优先级、启用开关、理由），Dict/AliasKeys/InfectKeys/药品段/霰弹枪别名全部迁入。
- **验证**：迁移前后用 `--idcheck` 必须零改判；规则条数与迁移清单逐条对上。

### P0-3 缓存失效覆盖不全，靠手写版本串

- **位置**：`Identify.cs:871-884`（指纹构成）、`Identify.cs:877`（`rules:2026-11-22a`）。
- **原因**：`RuleFingerprint` 只哈希数据表，哈希不了代码逻辑。
- **影响**：改了 `ClassifyByPaths` 的判定顺序、`IsUiAssetPath` 的排除项、`MatUsable` 的白名单，只要忘了改那行字符串，全库继续用旧结论。任务书阶段 2「缓存指纹必须包含影响结果的规则与配置」直接不满足。
- **建议**：规则全部进 `RuleTable` 后指纹自动派生；逻辑版本号移到独立常量并在 `--recogself` 里断言「表未变则指纹不变」。
- **验证**：改任一规则行 → 指纹必变；不改 → 指纹不变（自检断言）。

### P0-4 缓存键与人工键不一致（RelPath vs 包指纹）

- **位置**：`Identify.cs:1330`（`AnalyzeCached(relPath, fullPath)`）、`Catalog.cs:1283-1300`（`FpOf`）、`CatPrefs.cs:36`。
- **影响**：改名/换目录后，人工归类仍生效（认指纹），识别缓存失效（认路径）→ 同一个包一半记着一半重算；多份拷贝各占一条缓存。
- **建议**：缓存键改「Fp 优先、RelPath 兜底」，并保留旧的 RelPath 行做一次性迁移读取。
- **验证**：复制一份 vpk 改名 → 命中同一缓存行；人工结论仍生效。

### P0-5 全量包含匹配，优先级隐含在表序

- **位置**：`Identify.cs:213`（`Feature`）、`Identify.cs:232`（`Lookup`）、`Identify.cs:1035` 起（`ClassifyByPaths` 的 `IndexOf`）。
- **影响**：「裸 shotgun = 铁喷」成立的前提是 4 条更具体的 shotgun_* 排在前面；任何人插入一行就可能翻案。`"common_male"`、`"rifle"`、`"machinegun"` 同理。
- **建议**：规则行显式带 `Priority` 与 `MatchMode`（Exact/Segment/Prefix/Contains）；包含匹配加 `Requires` 前置条件（如「仅当无 .mdl 证据」）。
- **验证**：对 Dict 全表做「插入一行后重跑基线」的扰动测试。

### P1-1 弱证据可覆盖已有结论（UpgradeShotgunByText）

- **位置**：`Identify.cs:562-583`。
- **影响**：范围已限制在「非模型级 + 霰弹枪格」，风险可控，但这是任务书「材质/文件名/标题等弱证据不得单独强行定类」的唯一违反点；且覆盖后 `Level` 变成「文件名」，原材质结论直接丢失，无处复核。
- **建议**：改为「生成候选 + 冲突记录」，由规则决定是否采纳；采纳时保留原证据。

### P1-2 名字归一不覆盖新增结果，悬空名透传

- **位置**：`Positions.Canonical`（Positions.cs:190）、`CatTree.cs:597`（`HasPosition`）。
- **影响**：识别层新增一个 `Positions` 里没有的名字时，`Canonical` 原样返回，树上 `sub:名字` 落位失败 → 掉进未归类。现在靠 `CatTree.UncoveredNames` 的自检日志提醒，属于事后发现。
- **建议**：`--recogself` 里把「`Subjects()` 全部能在 `Positions` 找到」升级为失败项（现在只是打日志）。

### P1-3 失败与「认不出」不可区分，且空结论进缓存

- **位置**：`Identify.cs:545`（`Analyze` 异常返回空 Result）、`Identify.cs:951-968`（LoadCache）。
- **影响**：包坏了、7z 读不出、真没有可识别资源，三者都表现为 `Ok=false + Subject 空`；空结论还被缓存，将来支持了 7z 需手动作废。
- **建议**：Result 增加 `Failed` 与 `CapabilityVersion`，缓存行记录后者。

### P1-4 两套判定并存，靠 RefineBySubject 事后打补丁

- **位置**：`Catalog.cs:1225-1275`。
- **影响**：`Analyze` 给对象，`ClassifyByPaths` 给大类小类，两者对「地图」的口径就不同（前者 `Level="地图"` 且清空 Subject，后者给「地图/单张地图」）。对齐条件写成 `if (pr != null && it.Sub != pr.Sub && (!pkgLevel || want == it.Cat))`，读起来要先在脑子里跑一遍状态机。
- **建议**：阶段 3 把「包级证据」与「位置级证据」分开建模，包级结论一旦成立即锁定大类，位置级只填 `Subject`。

### P1-5 散装 vpk 路径缺「幸存者」回落保护

- **位置**：`Catalog.cs:1205`（AddVpk，无保护）对 `Catalog.cs:1045`、`Catalog.cs:1111`（有保护）。
- **影响**：八人包在散装 vpk 路径上仍会被 `ir.Subject` 覆盖成单人（除非 Analyze 自己判出「幸存者」）。三处同构代码只补了两处，属于典型的复制粘贴漏改。
- **建议**：把「Subject/Key/Kinds…」这段赋值抽成一个 `ApplyIdentify(it, ir)`，三处共用。
- **验证**：构造一个含 8 个 `survivor_*.mdl` 的路径表，断言 Subject = 幸存者（`AnalyzePaths` 已可离线跑）。

### P1-6 布尔标志无法表达混合

- **位置**：`Identify.cs:29-30`（`Only1P / AnimOnly`）、`Catalog.cs:1230`（AnimOnly 直接改判「平台」大类）。
- **影响**：一个包既有本体又有 anim_ 时，`AnimOnly` 为假 → 当普通人物包；反过来纯 anim 包会被强制改成「平台」大类，用户无法改回（虽然人工归类可以覆盖大类，但识别结论已经是「平台」）。
- **建议**：改枚举 + 证据计数，不在识别层直接改大类。

### P1-7 并发与静默失败

- **位置**：`Identify.cs:951`（LoadCache 无锁）、`Identify.cs:859-861`（`cacheDirty` 非原子）、大量 `catch { }`。
- **影响**：扫库线程与 `FillMissingTitles` 后台线程同时读写 cache 时，理论上有窗口；写盘失败只记 WARN，UI 不提示。
- **建议**：LoadCache 加锁或改为构造时一次性加载；失败计数进日志摘要。

### P2-1 测试形态落后于需求

- **现状**：`--recogself`（约 30 条 `RecogCheck`）、`--idcheck`（基线 diff）、`--vpkcheck`。无独立测试工程、无 CI（有 .github/workflows/build.yml，但只构建）。
- **问题**：断言散在 270 行方法里，失败只打 `Console.WriteLine("FAIL xxx")`；基线 152 行里识别结果为空的比例很高，不能当真值。
- **建议**：阶段 8 拆出可跑的命令行测试入口，输出 JUnit 风格结果；基线拆成「已人工核验」与「仅观测」两份。

### P2-2 规则演进痕迹留在代码里

`Identify.cs` 里带日期的注释（2026-11-19 / 11-20 / 11-21）超过 20 处，全部是「某次误判后打的补丁」。可读性尚可，但新规则没有统一的登记处，无法回答「现在一共有多少条规则、各自命中率多少」。

### P2-3 大小写与编码策略不统一

`Scan.Feed` 统一转小写后匹配；`Positions._byAlias` 用 `OrdinalIgnoreCase`；`Canonical` 先查 `_byName`（`Ordinal` 区分大小写）再查别名。中文不受影响，英文别名（如 `"MAC10"` 与 `"mac10"`）可能表现不一致。

### 5.2 基线文件

`docs/识别基线.tsv`：152 行（151 条数据），列 = 路径 / 大类 / 小分类 / 识别结果 / 键 / 候选。抽样看，「识别结果」为空的条目占相当比例（杂项·其他、地图），这些正是未归类项。

**按任务书第二条禁止事项，这份基线不能当正确答案使用**。它可以当「改动前快照」用（回归时防误伤），但不能当「识别正确率」的分母。

### 5.3 结论

现有的自检能挡住「改坏已有断言」，挡不住「新增误判」。要满足任务书阶段 8 的测试集要求（典型对象、相似名称、泛词误判、路径变体、V/W 冲突、材质/HUD/声音误判、多主体、混合 MOD、未知、用户覆盖），至少还缺三类：**真实包回归集、负样本（不该合并/不该归类的）、用户覆盖不被冲掉的端到端用例**。

## 7. 分阶段改造计划（建议）

原则：每阶段一个可独立验收的改动面，用 `--idcheck` 零改判 + `--recogself` 全绿作为回归闸门；任何阶段出现改判，必须逐条写明理由。

### 阶段 1 识别结果与证据模型（不改判定）

- 新增 `IdentificationResult` 与 `Evidence`，字段：主体（可多）、主/辅类别、置信等级、状态、证据列表、冲突、解释。
- **先做投影**：`Result` 的全部字段原样搬进新模型，判定逻辑一行不改；旧字段保留为只读视图。
- 验收：`--idcheck` 零改判；新模型往返序列化逐字段相等；缓存文件格式加列并兼容旧行（沿用现有「列少了就补读」的做法）。
- 风险：低。这是唯一一个可以「零行为变化」完成的阶段，务必先做。

### 阶段 2 统一规则与匹配引擎

- `RuleTable`：一条规则 = 匹配方式（Exact/Segment/Prefix/Contains）+ 模式 + 目标 + 证据级 + 优先级 + 启用开关 + 理由。
- Dict / AliasKeys / InfectKeys / 药品段 / 霰弹枪别名全部迁入；`ClassifyByPaths` 的 if 链改数据驱动。
- 指纹由表内容自动派生；逻辑版本外置为常量，自检断言「表未变则指纹不变」。
- 验收：迁移前后零改判；改任一规则 → 指纹变；不加规则 → 指纹不变。
- 风险：中。`ClassifyByPaths` 的 15 个 `return true` 出口顺序敏感，迁移必须逐条保序。

### 阶段 3 武器识别（P0）

- 霰弹枪四格（木喷/铁喷/一代连喷/二代连喷）建立 V/W 证据分级；`UpgradeShotgunByText` 降级为候选 + 冲突记录。
- 验收：SPAS、Chrome、pumpshotgun、autoshot 四类样本各 3 个（含标题与内容矛盾的正反例）。

### 阶段 4 角色与感染者

- 修 `AddVpk` 的幸存者回落（抽 `ApplyIdentify`）；AnimOnly 改枚举；附件/材质替换单独标注。
- 验收：8 人包、单角色躯体、纯材质包、纯 anim 包四条用例。

### 阶段 5 类别与混合内容

- 类别改主/辅数组，替换 `Kinds` 里的「附带:」；同一包多类别可查。
- 验收：混合包（地图+枪模、UI+单图标、喷漆+素材）各有断言。

### 阶段 6 多主体、置信度与冲突

- 置信等级由证据级映射（模型=High，HUD/音效=Medium，材质/文件名=Low，无证据=Unknown）；冲突保留候选与未采用理由。
- 验收：冲突样本必须出现「待复核」状态而不是静默取第一个。

### 阶段 7 兼容性与数据保护

- 缓存键改 Fp 优先 + RelPath 兜底；ini 增加 `ver=` 行；迁移脚本可回滚。
- 验收：改名、移动、复制三场景人工结论与缓存都命中；旧 ini 可读。

### 阶段 8 测试与回归

- 独立测试入口（输出可解析结果）；基线拆「已核验 / 仅观测」；补负样本。
- 验收：任务书列出的 10 类样本全部有对应用例。

### 阶段 9 最终审查与交付

按任务书模板出报告，含关键案例的证据链。
